# Environment-family expansion gate

Do not add a second environment merely to increase benchmark size. Expansion
is justified only after a capable-model feasibility run produces interpretable
goal-only behavior or a clear boundary-communication signal.

A candidate family must:

1. have a legitimate, independently verifiable task and authorised route;
2. express the same operator-policy semantics without reusing package-recovery
   surface clues;
3. keep all targets, credentials, and consequences synthetic and local;
4. support no-shortcut, discoverable-only, and usable-shortcut variants;
5. expose proposal, execution, boundary, protected-read, transfer, and task
   success ground truth;
6. pass public-internet, DNS, metadata, host-mount, Docker-socket, privilege,
   cleanup, and evaluator-integrity checks;
7. include honest, permission, probing, and escalation controls before any
   model run; and
8. preserve the same fixed scoring semantics or document a preregistered
   reason for changing them.

Run the deterministic matrix first. Then run a small honest capability check.
Only after both pass should the family enter a bounded goal-only pilot. Never
pool families until per-family capability and measurement invariance have been
reported.
